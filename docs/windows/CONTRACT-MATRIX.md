## Convenciones

- `T` es el tipo indicado por `invoke<T>` en `api.ts`; `void` resuelve `null` en el protocolo socket. Campos opcionales aceptan omisión/null según wrapper Rust y `arg<Option<T>>`.
- Tauri rechaza con string cuando handler devuelve `Err(String)`; daemon serializa `ErrorBody { code, message }`. `arg<T>` falla como `bad_params`; error de dominio usa `failed`. Para comandos sin error Rust explícito, error de transporte/serialización sigue siendo posible. No se afirma equivalencia exacta de texto ni semántica de error.
- Las firmas siguientes transcriben el contrato frontend tipado (`api.ts`) con llaves camelCase wire. La semántica / errores de dominio se conservan en implementaciones fuente; se anotan abajo las diferencias comprobadas.

## W21 — host Tauri/WebView2 y media-controls Windows

Estado: el host Tauri para targets no Linux existe en `src-tauri`; Wry/Tauri proporciona el WebView2. No hay integración WebView2 propia ni ejecución runtime Windows verificada por los tests de este checkout.

- **Dispatch/IPC**: Windows arranca `src-tauri/src/main.rs` → `app_lib::run()`. El flujo es `ui/src/lib/api.ts` (`invoke`/`listen`) → `src-tauri/src/commands.rs` y `TauriSink` → `AppState` en el mismo proceso. El daemon `ryotunesd` y `ryotunes_protocol` usan Unix sockets y no participan en el flujo Windows; no se debe inventar un adaptador de socket para W21.
- **Errores**: en este host los `Result<T, String>` de comandos Tauri rechazan con string; el `ErrorBody {code,message}` y `bad_params`/`failed` pertenecen al protocolo socket Linux. El frontend debe conservar el rechazo Tauri; no existe una normalización que se haya probado entre esos hosts.
- **Eventos/readiness**: `TauriSink` usa `AppHandle::emit`; `ui/src/routes/+layout.svelte` instala los listeners en `initApp` y llama `frontend_ready` con reintentos desde `onMount`. El failsafe nativo `arm_reveal_failsafe` solo se agenda bajo `cfg(target_os = "linux")`; Windows depende del handshake Svelte y hoy no tiene recuperación nativa verificada si el WebView no monta. No se probó la entrega real con WebView2 ni un arranque Windows limpio.
- **HWND/SMTC**: el defecto confirmado era `crates/core/src/media.rs::run` fijando `hwnd=None`; souvlaki 0.8.3 hace panic al construir Windows `MediaControls` sin HWND. Corregido: Tauri obtiene `main.hwnd()` durante setup, lo convierte a `MediaWindowHandle(NonZeroUsize)` y lo pasa como valor opaco al thread owner de SMTC; `spawn` no crea ese thread si el HWND falta. El core no comparte un HWND mutable ni lo bloquea. Windows oculta `main` al cerrar y el camino normal Quit espera el teardown de `MediaHandle` antes de `app.exit`; el host no recrea `main`. `cargo test --locked -p ryotunes-core media::tests` (Linux 1/1) valida el wrapper nulo/no nulo; el test cfg Windows de fallo fail-soft está añadido pero pendiente. Ninguno prueba un HWND real, COM o SMTC.
- **Taskbar vs SMTC**: `src-tauri/src/taskbar.rs` es otra API (COM `ITaskbarList3`), consulta su HWND en el hilo Tauri y agenda actualizaciones con `run_on_main_thread`; estos botones no prueban SMTC ni WebView2.
- **Build/runtime**: se ejecutó `cargo build --locked -p ryotunes --package ryotunesd` en Linux; compila el host Linux, no la rama `cfg(windows)`. No se ejecutaron Windows/MSVC ni una ventana WebView2 en esta tarea (entorno Linux). `src-tauri/tauri.windows.conf.json` requiere `src-tauri/libmpv-2.dll`, ausente en el checkout. W21 sigue parcial hasta build reproducible, startup limpio, invoke/eventos WebView2 reales, controles SMTC y cierre/reinicio probados en Windows 11.
