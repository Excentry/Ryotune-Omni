# Compilacion propia de libmpv GPL Windows x64 con fuentes transitivas

Investigacion de solo lectura, 21 de octubre de 2026. No se ejecuto ninguna compilacion, no se cambio el binario seleccionado y no se modificaron CI ni implementacion. Implementacion futura: Excentry, propietario de dependencias nativas y CI. Las propuestas siguientes requieren delegacion expresa.

## 1. Que permite la receta oficial y que falta para cerrar sus entradas

### Takeaway

La alternativa mas cercana al artefacto seleccionado es una compilacion propia en CI Linux remoto usando la receta oficial de mpv, modificada para consumir exclusivamente un conjunto cerrado de fuentes. No exige instalar Linux localmente, pero fijar solamente el SHA de mpv y el digest del contenedor NO fija ni entrega todas las fuentes transitivas.

### Cited Findings

- Punto de partida indicado por el coordinador: mpv `a43ab319fdb7aec31874999e5562c9975328cbda`, FFmpeg `ca85613d10cd523dd05780f48dc6ecac142bd560`, imagen `ghcr.io/btbn/ffmpeg-builds/win64-gpl@sha256:666d6b74870f232bbc9ea29acc608c91b6b1c74f1effd8129cd39ed2332d1287`. Estos identificadores se conservan como antecedentes, no como demostracion de una reconstruccion identica. La documentacion del commit de mpv confirma que sus paquetes completos Windows se construyen sobre imagenes BtbN con toolchain y bibliotecas estaticas. [Documentacion Windows fijada](https://github.com/mpv-player/mpv/blob/a43ab319fdb7aec31874999e5562c9975328cbda/DOCS/compile-windows.md)
- `ci/build-mingw64-full.sh` usa clones superficiales del HEAD de FFmpeg y libsixel, rama `v2.1` de LuaJIT, etiquetas para cppwinrt/windows-rs y `meson wrap install mujs` seguido de `meson subprojects download`. Sus argumentos fuerzan `libmpv=true` mediante build-common, biblioteca compartida para mpv y preferencia por dependencias estaticas. En variante GPL habilita expresamente `dvda,dvdnav,rubberband`. Por tanto el SHA de la receta no basta para fijar los componentes descargados al ejecutarla. [Receta exacta](https://github.com/mpv-player/mpv/blob/a43ab319fdb7aec31874999e5562c9975328cbda/ci/build-mingw64-full.sh), [helper exacto](https://github.com/mpv-player/mpv/blob/a43ab319fdb7aec31874999e5562c9975328cbda/ci/build-common.sh)
- `build_subrandr` clona HEAD de `afishhh/subrandr` y ejecuta `cargo xtask install`; el helper no fuerza modo locked/offline ni conserva dependencias Cargo como entregable. [Helper exacto](https://github.com/mpv-player/mpv/blob/a43ab319fdb7aec31874999e5562c9975328cbda/ci/build-common.sh)
- El empaquetado oficial copia DLL, import library GNU `.dll.a`, headers, LICENSE.GPL o LICENSE.LGPL y un JAR libbluray. No incluye en esa fase un archivo de fuentes transitivas ni un inventario completo de licencias. El JAR tambien debe entrar en el inventario si se redistribuye. [Packaging oficial](https://github.com/mpv-player/mpv/blob/a43ab319fdb7aec31874999e5562c9975328cbda/ci/build-mingw64-full.sh)
- Se inspecciono BtbN en `937868360a21d711ec94a33f5591d345ad9b7754`, revision resuelta durante esta investigacion; NO se ha demostrado que sea la que genero el digest seleccionado. Su `download.sh` crea `.cache/downloads/<stage>_<hash>.tar.xz` y un enlace por stage. El hash del nombre se calcula sobre el TEXTO del comando de descarga, no sobre los bytes descargados. Un ref mutable dentro de ese comando puede producir contenido distinto con el mismo nombre de cache. [Descarga](https://github.com/BtbN/FFmpeg-Builds/blob/937868360a21d711ec94a33f5591d345ad9b7754/download.sh)
- El cache BtbN es realmente aprovechable: el descargador predeterminado usa SCRIPT_REPO/SCRIPT_COMMIT y `git-mini-clone`, que hace fetch superficial del ref, checkout de FETCH_HEAD y deja el checkout en el tar. `generate.sh` referencia dichos tar; `run_stage.sh` los extrae para compilar y elimina el directorio de trabajo al terminar. Es necesario preservar el cache ANTES de limpieza; el contenedor final no equivale al paquete de fuentes. [Funciones de descarga](https://github.com/BtbN/FFmpeg-Builds/blob/937868360a21d711ec94a33f5591d345ad9b7754/util/dl_functions.sh), [git-mini-clone](https://github.com/BtbN/FFmpeg-Builds/blob/937868360a21d711ec94a33f5591d345ad9b7754/images/base/git-mini-clone.sh), [Generador](https://github.com/BtbN/FFmpeg-Builds/blob/937868360a21d711ec94a33f5591d345ad9b7754/generate.sh), [Runner de stages](https://github.com/BtbN/FFmpeg-Builds/blob/937868360a21d711ec94a33f5591d345ad9b7754/util/run_stage.sh)
- Reconstruir la imagen BtbN tampoco es cerrado por defecto: base Ubuntu por etiqueta, apt update/dist-upgrade, NodeSource remoto, pip meson sin version, rustup remoto y cargo install cargo-c. `makeimage.sh` ejecuta descarga y generacion y utiliza caches de compilacion separados del cache de fuentes. [Base Dockerfile](https://github.com/BtbN/FFmpeg-Builds/blob/937868360a21d711ec94a33f5591d345ad9b7754/images/base/Dockerfile), [makeimage](https://github.com/BtbN/FFmpeg-Builds/blob/937868360a21d711ec94a33f5591d345ad9b7754/makeimage.sh)

### Inferences

- Recomendacion: conservar primero el binario actual como candidato sin declarar resuelta su procedencia. Si no se recupera el cache exacto y la revision del productor correspondientes al digest, construir un candidato NUEVO con identidad y procedencia propias; no presentar fuentes de una compilacion nueva como fuentes probadas del DLL anterior.
- Dos vias para cerrar la capa precompilada: (A) recuperar fuentes exactas, parches y receta verificables del digest existente; (B) reconstruir las dependencias BtbN desde una revision elegida y cerrada, archivando su cache. A reduce trabajo solo si existe evidencia suficiente; B es el fallback controlable y exige aprobacion para cambiar el candidato binario.
- Distinguir tres objetivos: fuentes correspondientes completas; entradas fijadas y rebuild sin descargas; igualdad bit a bit. Los dos primeros no prueban el tercero. Fechas, rutas, orden de archivos, identificadores PE y toolchain pueden requerir trabajo adicional de reproducibilidad.

### Gaps

- No se inspeccionaron las capas OCI del digest ni su metadata/provenance. No se conoce en esta investigacion el commit BtbN que lo produjo ni la disponibilidad del cache exacto. No se afirma imposible recuperarlo.
- No se produjo inventario exhaustivo de todos los stages ni se evaluaron todas las licencias. Una receta visible en GitHub no demuestra por si sola correspondencia con el artefacto seleccionado.

## 2. Ofrecen los builders Windows existentes una solucion de fuentes ya terminada

### Takeaway

`shinchiro/mpv-winbuild-cmake` es una alternativa tecnica real, con descarga centralizada de fuentes y CI remoto, pero el workflow inspeccionado NO publica un paquete completo de fuentes correspondientes. Adoptarlo no elimina el trabajo de congelar refs, archivar fuentes, revisar notices y validar un nuevo DLL.

### Cited Findings

- Revision inspeccionada: `1f8d2e76255abc48f0456d9be99b4cab9c6566e6`, obtenida de la API durante la investigacion, no una suposicion basada en una release fechada. README documenta Linux, Cygwin y MSYS2, `SINGLE_SOURCE_LOCATION`, `ninja download` y un `ninja update` que actualiza repositorios Git. [Commit](https://github.com/shinchiro/mpv-winbuild-cmake/commit/1f8d2e76255abc48f0456d9be99b4cab9c6566e6), [README fijado](https://github.com/shinchiro/mpv-winbuild-cmake/blob/1f8d2e76255abc48f0456d9be99b4cab9c6566e6/README.md)
- Su workflow clang ejecuta en ubuntu-latest con contenedor Arch `latest`; checkout/actions apuntan a refs mutables; usa cache `src_packages`, hace `ninja download || true` y despues `ninja update`. Los uploads inspeccionados contienen binarios/debug y logs, mientras los fuentes quedan en cache. Los logs tienen retencion de un dia; el workflow ademas poda releases antiguas. Nada de ello constituye un archivo publico y duradero de fuentes por DLL. [Workflow exacto](https://github.com/shinchiro/mpv-winbuild-cmake/blob/1f8d2e76255abc48f0456d9be99b4cab9c6566e6/.github/workflows/mpv_clang.yml)
- `mpv.cmake` habilita libmpv y Rubber Band y copia `libmpv-2.dll`, `.dll.a` y headers. `rubberband.cmake` consume la rama `default`, enlaza estaticamente con FFT builtin y libsamplerate. Esto difiere del stage BtbN inspeccionado, que selecciona FFTW y libsamplerate; cambiar de builder cambia la composicion, aunque ambos tengan pitch. [mpv](https://github.com/shinchiro/mpv-winbuild-cmake/blob/1f8d2e76255abc48f0456d9be99b4cab9c6566e6/packages/mpv.cmake), [Rubber Band shinchiro](https://github.com/shinchiro/mpv-winbuild-cmake/blob/1f8d2e76255abc48f0456d9be99b4cab9c6566e6/packages/rubberband.cmake), [Rubber Band BtbN](https://github.com/BtbN/FFmpeg-Builds/blob/937868360a21d711ec94a33f5591d345ad9b7754/scripts.d/50-rubberband.sh)
- El packaging incorpora otro repositorio, `shinchiro/mpv-packaging`, sin SHA explicito y copia material adicional como `d3dcompiler_43.dll`. Su instalacion de ExternalProject descarga tambien un archivo CMake desde etiqueta remota sin verificacion de contenido en el comando inspeccionado. No basta congelar solo packages/mpv.cmake. [Packaging](https://github.com/shinchiro/mpv-winbuild-cmake/blob/1f8d2e76255abc48f0456d9be99b4cab9c6566e6/packages/mpv-packaging.cmake), [ExternalProject](https://github.com/shinchiro/mpv-winbuild-cmake/blob/1f8d2e76255abc48f0456d9be99b4cab9c6566e6/cmake/download_externalproject.cmake)
- CMake recomienda GIT_TAG como commit hash frente a ramas/tags para trazabilidad y repetibilidad; URL_HASH comprueba bytes descargados. UPDATE_DISCONNECTED no impide la descarga inicial. Consultado tambien mediante Context7. Advertencia: shinchiro parchea ExternalProject, por lo que debe comprobarse su comportamiento concreto al adaptar estas opciones. [Documentacion oficial CMake](https://cmake.org/cmake/help/latest/module/ExternalProject.html)

### Inferences

| Via | Ventaja concreta | Trabajo que sigue pendiente | Recomendacion |
| --- | --- | --- | --- |
| Receta oficial mpv + BtbN controlado | Menor desviacion conceptual del candidato actual; descarga BtbN ya separada por stage | Cerrar capa BtbN y descargas mpv; emitir fuentes/notices; gates Windows | Primera opcion para Excentry |
| Fork fijado de shinchiro | Fuentes centralizadas; bootstrap completo; libmpv/Rubber Band explicitos | Congelar muchos repos y toolchain; sustituir cache por entregable; cerrar packaging; revalidar distinto DLL | Alternativa si mantener bootstrap resulta preferible |
| Descargar otro DLL del builder | Evita compilacion inmediata | No resuelve automaticamente correspondencia, retencion de fuentes ni compatibilidad | No reemplazar silenciosamente |

- No se encontro una emision completa de fuentes en los scripts y workflow inspeccionados de shinchiro; no es una afirmacion universal sobre cualquier archivo historico alojado por el proyecto. Obtener fuentes del productor sigue siendo una via posible si entrega el conjunto exacto y evidencia de correspondencia.
- Alcance razonable expresado en entregables, no horas inventadas: cierre del grafo de entradas, captura/mirror de fuentes, adaptacion de build offline, inventario legal, compilacion candidata y validacion Windows. La primera opcion reutiliza mas del camino oficial; la segunda añade bootstrap y comparacion funcional de otra composicion.

### Gaps

- No se descargaron todos los archivos de SourceForge ni todos los assets de todas las releases. No se afirma que ningun builder del ecosistema publique nunca fuentes; solo que la alternativa concreta inspeccionada no cierra el problema por defecto.
- No hay mediciones propias de duracion, costo, almacenamiento o tasa de fallo. Los tiempos orientativos del README no se extrapolan a esta infraestructura.

## 3. Plan accionable, entregables y gates para Excentry

### Takeaway

Proponer una CI de construccion Linux remota y otra de validacion Windows x64 MSVC, sin entorno Linux local. La aceptacion debe exigir un candidato identificado, fuentes verificadas y notices por componente, reconstruccion sin red de fuentes y pruebas reales de importacion y pitch; no solo que Meson termine.

### Cited Findings

- El manual de mpv documenta `rubberband` como filtro de pitch independiente del speed, `pitch-scale`, motores faster/finer y comandos dinamicos set-pitch/multiply-pitch. La receta oficial habilita la dependencia en variante GPL. [Manual del commit](https://github.com/mpv-player/mpv/blob/a43ab319fdb7aec31874999e5562c9975328cbda/DOCS/man/af.rst), [Receta](https://github.com/mpv-player/mpv/blob/a43ab319fdb7aec31874999e5562c9975328cbda/ci/build-mingw64-full.sh)
- mpv documenta enlazar programas MSVC con libmpv; para DLL MinGW permite generar `.def` con gendef y crear `mpv.lib` con `lib /def:libmpv-2.def /name:libmpv-2.dll /out:mpv.lib /machine:x64`. El nombre debe coincidir con el DLL y la arquitectura con el destino. No equivale a compatibilidad de enlace estatico entre compiladores. [Enlace MSVC, documento exacto](https://github.com/mpv-player/mpv/blob/a43ab319fdb7aec31874999e5562c9975328cbda/DOCS/compile-windows.md#linking-libmpv-with-msvc-programs)
- Copyright de mpv advierte que bibliotecas enlazadas tambien cambian las obligaciones de licencia. GPLv3 define Corresponding Source incluyendo scripts necesarios y exige acceso equivalente para distribucion por descarga; deben revisarse las licencias efectivas de cada componente, no deducir una version GPL del nombre `win64-gpl`. [Copyright mpv](https://github.com/mpv-player/mpv/blob/a43ab319fdb7aec31874999e5562c9975328cbda/Copyright), [GPLv3, secciones 1 y 6](https://www.gnu.org/licenses/gpl-3.0.html)

### Inferences

Plan propuesto; no ejecutado ni autorizado como implementacion:

1. **Gate de procedencia.** Excentry decide si puede recuperar el productor y fuentes del digest existente. Si no, solicita aprobacion para construir otro candidato, manteniendo hashes y nombres separados del DLL anterior. Elegir arquitectura x64 y baseline CPU explicitamente; no introducir x86-64-v3 sin decision de compatibilidad.
2. **Lock de entradas.** Crear manifiesto por componente con URL, ref observado, commit completo resuelto, submodules recursivos, SHA-256 del archivo efectivamente preservado, parches y sus hashes, licencia y rol (enlazado/runtime/herramienta). Incluir FFmpeg indicado, LuaJIT, libsixel, subrandr, cppwinrt, windows-rs, wraps y packagefiles de Meson y todas las bibliotecas enlazadas del contenedor. Un tag de version o una rama no son el lock definitivo. Cualquier entrada no resuelta debe detener el build candidato.
3. **Fuentes antes de compilar.** Ejecutar fase de adquisicion controlada; archivar `.cache/downloads` de BtbN con hashes de CONTENIDO, mas fuentes descargadas por mpv, wraps, submodules y dependencias Cargo transitivas. Capturar las descargas ocultas en configure/build; no limitarse a los clones evidentes. Si se usan clones parciales, materializar los blobs necesarios antes de cortar la red; un archivo .git con promisor remoto no es autosuficiente. Conservar tanto fuentes originales como parches/aplicacion reproducible y cualquier archivo generado no regenerable a partir del conjunto archivado.
4. **Cerrar entorno.** Fijar acciones por SHA y contenedores/toolchains por digest, versionar archivos cross y opciones. Si se reconstruye la imagen base, congelar tambien paquetes, repositorios/snapshots, herramientas Python/Rust/Node y descargas auxiliares. Conservar imagen OCI o mirror durable cuando se dependa de ella. Separar exigencia tecnica de reproduccion del entorno de los limites legales de Corresponding Source y System Libraries; no afirmar que cada herramienta del host deba redistribuirse como fuente legalmente.
5. **Compilar desde fuentes preservadas.** Adaptar la receta oficial para no clonar HEAD ni consultar WrapDB en la fase de compilacion; consumir manifiesto y almacenamiento local verificado. Usar configuracion Cargo bloqueada/offline donde corresponda y eliminar adquisicion implicita. Reconstruir desde checkout limpio sin cache de objetos; bloquear red durante la fase de build. Si algun componente necesita red, aun no se ha cerrado el grafo.
6. **Emitir entregables vinculados al mismo build.** `libmpv-windows-x64-<build-id>.zip` con DLL, headers e import library adecuada; `libmpv-corresponding-source-<build-id>.tar.xz` con fuentes originales completas, parches, fuentes vendorizadas, scripts/build/configuracion y README de reconstruccion; `sources.lock.json`; `SHA256SUMS`; inventario/SBOM; `THIRD-PARTY-NOTICES` y `licenses/` conservando copyrights, avisos y textos reales por componente; logs/configure/meson introspection y evidencia de la composicion final. Si se incluye el JAR de libbluray u otros binarios auxiliares, tratarlos expresamente, no olvidarlos por estar fuera del DLL.
7. **Gate MSVC real en Windows limpio.** Examinar PE x64, exports y dependencias importadas; generar/probar `mpv.lib` con el nombre esperado por el consumidor, sin asumir que `.dll.a` basta. Compilar y enlazar un consumidor con toolchain Windows MSVC, cargar el DLL, comprobar client API, crear/inicializar/destruir handle y reproducir fixture. Probar despues consumidor Rust `x86_64-pc-windows-msvc` y el host Tauri cuando se autorice. Verificar dependencias de DLL ausentes y busqueda de DLL en instalacion portable sin MSYS2/MinGW del desarrollador en PATH.
8. **Gate Rubber Band y regresiones.** Verificar en configuracion y ejecucion el filtro nativo `rubberband`, no solo el filtro homonimo de FFmpeg. Probar pitch-scale 0.5/1/2, cambios en vivo y tempo independiente; probar conservar ganancia/loudness, quitar pitch y rollback de errores. La receta habilitada no prueba por si sola que el DLL cargado por la app sea ese candidato. Asociar pruebas al SHA-256 del DLL efectivo. Las pruebas semanticas/del filtro no prueban calidad acustica; una medicion de fixture tonal puede comprobar desplazamiento de frecuencia si se necesita ese nivel de evidencia.
9. **Gate de entrega.** Auditar todas las bibliotecas realmente incorporadas, licencias/notices, fuentes y scripts; probar reconstruccion desde el paquete publicado propuesto en infraestructura limpia. No usar cache efimero de Actions como unica custodia de fuentes. En una publicacion futura autorizada, situar enlaces claros a fuentes correspondientes junto al binario y preservar ambos de forma duradera. No publicar mientras falten fuentes verificadas o aprobacion de cambio de candidato.

Criterio minimo de salida de la investigacion a implementacion: propietario Excentry acepta el plan; identificador del nuevo candidato aprobado; lista de entradas cerrada; ubicacion de archivo de fuentes definida; gates MSVC y Rubber Band acordados. No se requiere tocar ahora backend, manifests Cargo, empaquetado ni CI desde esta tarea.

### Gaps

- Ningun gate se ejecuto: no hay prueba nueva de build Windows, ABI, reproduccion, audio ni reconstruccion bit a bit. El proyecto sigue sin validacion de plataforma atribuible a esta investigacion.
- No se resolvio version de licencia efectiva del conjunto seleccionado ni se emitio dictamen juridico. GPLv3 se cita por su definicion y mecanismo concreto; deben revisarse tambien versiones aplicables y licencias de los componentes reales antes de distribuir.
- Inspeccion local limitada: `crates/player/src/lib.rs` contiene composicion nativa `rubberband=pitch-scale` y una regresion de ganancia/pitch, pero no se ejecutaron pruebas. La conversion/import library exacta que exige la integracion actual requiere inspeccion adicional por Excentry; no se afirma que baste cambiar nombre de un archivo.
